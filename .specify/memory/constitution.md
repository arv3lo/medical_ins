# Medical Ins Constitution

Platform between health centers and health insurers in Madagascar (OSTIE, BSA, …): patient records,
coverage requests, reimbursements and per-organization roles. These principles are the gates every
spec and plan is checked against. `CLAUDE.md` holds the day-to-day workflow and commands.

## Core Principles

### I. Every Action Is Audited, Atomically (NON-NEGOTIABLE)

- Every action that changes data, and every read of medical content, writes an `audit_logs` entry in
  the same database transaction as the action itself (`audit(tx, …)`).
- `audit_logs` is append-only, enforced by triggers on UPDATE, DELETE and TRUNCATE.
- Audit payloads hold identifiers and metadata only: ids, statuses, changed field names, dates.
  They MUST NOT contain medical text (examination, notes, vitals, diagnoses, reasons, addenda),
  password hashes or other secrets.

Rationale: the log can never be corrected or purged, and admins read it, so whatever it stores is
stored forever and shown to people who may not see medical content.

### II. Access Is Checked on the Server

- Every route calls `requireUser`, `requireSuperAdmin` or `requirePermission`. Hiding something in
  the UI is never the access check.
- The permission matrix lives only in `packages/shared/src/roles.ts`. A new permission goes there
  with a unit test.
- Business routes take the organization from the URL (`/api/organizations/:orgId/...`). A resource of
  another organization answers 404, not 403, so its existence isn't revealed.
- Super admin status grants only what the exhaustive allow-list in `roles.ts` names. A new
  permission fails to typecheck until it is classified.
- Only the super admin creates user accounts. Organization admins attach existing accounts.

### III. Medical Content Is for Care Roles Only

- Medical content is reachable only through `medical_record.*` and the other care permissions: care
  roles, never super admin status alone.
- Insurers see only what a decision needs: patient identity, and the acts, diagnosis and documents
  of the request being decided. Never the rest of the record.
- API responses to insurers use explicit projections. A table's columns are never spread into them.
- The one recorded exception: reception sees the appointment reason it enters.

### IV. Test-First (NON-NEGOTIABLE)

- Every behavior change starts with a test that is written and seen failing, then made to pass
  (red → green → refactor). A bug fix starts with a test that reproduces it.
- API behavior gets integration tests against a real PostgreSQL (`apps/api/test`, Fastify `inject`).
  Pure rules get unit tests next to their source.
- Concurrency rules get deterministic race tests: hold a lock in the test, then release it.
- Each acceptance criterion of a spec maps to at least one test.

### V. Data Integrity Under Concurrency

- State transitions read and check the row under `SELECT … FOR UPDATE`, or use a conditional
  `UPDATE … WHERE <expected state>` that answers 409 when no row changes.
- Invariants that must survive concurrency live in the database: unique indexes, exclusion
  constraints (`btree_gist`), CHECKs and triggers. Application checks only give friendly errors.
- Dates:
  - "Today" is the calendar date in `Indian/Antananarivo`.
  - Instants are stored in UTC.
  - Calendar dates are validated as real days.
- Money is stored as integer ariary (MGA). Amounts are computed on the server and never taken from
  the client.

### VI. Simplicity, and One Home for Each Rule

- KISS, YAGNI: no config knob, abstraction, parameter or export until something uses it. An
  abstraction needs two real callers.
- DRY: a rule used by both the API and the web app lives in `packages/shared`, and a server helper
  in `apps/api/src/lib`. Search those before writing a new one.
- Routes stay thin and delegate to `lib/` or a module service, with no route-to-route imports. Split
  files beyond ~500 lines.
- shadcn/ui components first. Colors come only from the theme tokens.

## Constraints

- **Stack:**
  - TypeScript strict, ESM, pnpm monorepo.
  - Fastify 5, Drizzle ORM and PostgreSQL 16.
  - React 19 with Vite, TanStack Query and React Router.
  - Self-hosted with docker-compose and Caddy, as one central instance.
- **Language:**
  - User-facing text (UI, API error messages) is in French.
  - Specs follow the roadmap's language (French).
  - Code, comments and commits are in English.
- **Context:**
  - Pages must stay usable on 3G connections (P6.7).
  - Personal data falls under Madagascar's law n°2014-038 (P6.5).
- **Migrations:** they are generated by drizzle-kit after every change to `apps/api/src/db/schema.ts`
  and committed. Custom SQL goes through `drizzle-kit generate --custom`.

## Development Workflow

- **Roadmap items and specs:**
  - `docs/ROADMAP.md` lists the items (`P3.1`, …). One item gives one branch (`feat/p3-1-…`) and one
    PR.
  - From P3 on, an item is specified with Spec Kit before any code: `/speckit-specify`, then
    `/speckit-clarify`, `/speckit-plan`, `/speckit-tasks`, `/speckit-analyze` and
    `/speckit-implement`.
  - Specs live in `specs/NNN-pX-Y-name/` (short name = the roadmap id plus a name). The roadmap item
    then links to its spec instead of repeating it.
- **Commits:**
  - Micro-commits, one logical change each, with conventional prefixes.
  - Branch before the first commit. Never commit to `main`.
  - No Claude/AI attribution in commits or PRs.
- **CI gates:** lint, typecheck, tests, Prettier and build pass locally before pushing. CI runs them
  on every PR.
- **Reviews:**
  - Results live only in `CODE_REVIEW.md`, overwritten by each review.
  - Each finding's outcome is recorded there, and the file is committed at the end of the fixes.

## Governance

- This constitution supersedes other practices. A plan that breaks a principle states the violation
  and its justification in the plan's Complexity Tracking table, or it is changed.
- Every plan's Constitution Check and every code review verify these principles.
- **Amendments:**
  - An amendment is a PR that changes this file, bumps the version and records the decision in the
    roadmap's decision log.
  - Versioning: MAJOR when a principle is removed or redefined, MINOR when one is added or
    materially expanded, PATCH for wording.
  - `CLAUDE.md` ("Rules that must hold") summarizes Principles I–III and is updated in the same PR.
